# تنظیمات محیط و منابع والکس

بررسی مستندات: ۲۰۲۶-۱۰-۲۲. این مرحله فقط آماده‌سازی تنظیمات است؛ کلاینت والکس، مخزن دادهٔ بازار، ایجنت و اجرای سفارش هنوز وجود ندارند.

## استفاده

فایل `.env` محلی ساخته شده و در Git نادیده گرفته می‌شود. نسخهٔ قابل اشتراک آن `.env.example` است. مقادیر خالی را در سیستم خودتان وارد کنید؛ کلیدها را در چت، فرانت‌اند یا متغیرهای `VITE_*` قرار ندهید.

```powershell
npm run env:check
npm run dev
```

Node فایل `.env` را سمت سرور می‌خواند. متغیرهای تعریف‌شده در محیط سیستم بر فایل اولویت دارند. تغییر فایل نیاز به راه‌اندازی مجدد سرور دارد. `env:check` هیچ درخواست شبکه‌ای ندارد و فقط نام تنظیمات ناقص و حضور/عدم حضور کلید را گزارش می‌کند. موفقیت آن، اعتبار کلید یا مجوز معامله را تأیید نمی‌کند.

در این نسخه فقط `PORT`، `NODE_ENV` و `SQLITE_PATH` رفتار سرور را تغییر می‌دهند. بقیه تنظیمات برای قرارداد اتصال آینده خوانده و اعتبارسنجی می‌شوند؛ هنوز موتور مصرف‌کننده ندارند. فعال‌کردن سوییچ‌های اتصال/ایجنت یا تغییر `TRADING_MODE` به shadow/live در این اسکلت با خطای روشن رد می‌شود. سقف‌های صفر یعنی تنظیم نشده، نه ریسک صفر و نه حفاظت اجرایی فعال.

## چیزهایی که باید تکمیل کنید

1. `WALLEX_API_KEY`: کلید مخصوص حساب اعتباری چالش، با دسترسی خواندن و معامله. برای endpointهای بررسی‌شده هدر `x-api-key` استفاده می‌شود؛ Secret/HMAC جداگانه‌ای در این قرارداد لازم نیست. تاریخ انقضای کلید را در `WALLEX_API_KEY_EXPIRES_AT` ثبت کنید.
2. `WALLEX_SUB_ACCOUNT_ID` و `WALLEX_PACKAGE_ID`: شناسه‌های تأییدشدهٔ حساب و طرح چالش؛ این‌ها صرفاً اطلاعات تطبیق حساب هستند و به‌عنوان هدر احراز هویت ارسال نمی‌شوند. فیلد `client_id` در **ثبت سفارش** شناسهٔ یکتای سفارش است و نباید با شناسهٔ حساب اشتباه گرفته شود.
3. `LLM_API_BASE_URL`، `LLM_API_KEY` و `LLM_MODEL`: مشخصات ارائه‌دهندهٔ انتخابی. قرارداد آینده در این فایل، Chat Completions سازگار با OpenAI است؛ اکنون کلاینتی پیاده نشده و سازگاری هیچ ارائه‌دهنده‌ای آزمایش نشده است. مدل یا سرویس پولی خاصی پیش‌فرض انتخاب نشده است.
4. `MARKET_DATA_SYMBOLS`: بازارهای داده برای تحلیل؛ `TRADING_ALLOWED_SYMBOLS`: فقط فهرست مجاز اعلام‌شدهٔ برگزارکننده. فعال بودن یک بازار در صرافی به معنی مجاز بودن آن در چالش نیست. `TRADING_BLOCKED_SYMBOLS` برای محدودیت‌های اضافه است. مقدار خالی مجوز معامله نیست.
5. زمان شروع و پایان دقیق با منطقه زمانی در `CHALLENGE_START_AT` و `CHALLENGE_END_AT`؛ مثلاً قالب `YYYY-MM-DDTHH:mm:ss+03:30`. تاریخ نمونهٔ داخل فایل زمان واقعی چالش نیست.
6. سقف سفارش، مجموع سرمایهٔ درگیر، افت سرمایه، حد ضرر و محدودیت spread/slippage پس از طراحی و آزمون استراتژی. واحد مبلغ تومان (`TMN`) است، نه ریال. BPS یعنی یک صدم درصد. درصدها مثل `2` یعنی دو درصد.

`WALLEX_ACCOUNT_TYPE=credit` انتخاب چالش است؛ قبل از معامله باید مطابقت کلید با حساب چالش به‌صورت خواندنی تأیید شود. این نام به‌تنهایی حساب را انتخاب یا عوض نمی‌کند. این اسکلت هیچ دریافت اعتبار جدید، انتقال وجه، اتصال کیف پول شخصی یا برداشت انجام نمی‌دهد.

## یافته‌های مستندات رسمی

- [ساخت کلید API](https://developers.wallex.ir/docs/create-api-key): هر حساب اصلی یا اعتباری کلید مختص خودش را دارد. کلید تاریخ انقضا و دسترسی مجزای خواندن/معامله/برداشت دارد.
- [ثبت سفارش](https://developers.wallex.ir/docs/spot-create-order): `POST /v1/account/orders`؛ `client_id` اختیاری اما یکتا، با حروف/اعداد/زیرخط؛ `price` و `quantity` رشته‌اند. محدودیت ثبت سفارش ۲۰ درخواست در هر ۱۰ ثانیه ذکر شده است. بودجهٔ محلی فایل ۱۰ است؛ این عدد محدودیت رسمی تمام endpointها نیست.
- [جزئیات سفارش](https://developers.wallex.ir/docs/spot-single-order-detail) و [لغو سفارش](https://developers.wallex.ir/docs/spot-cancel-order): `GET` و `DELETE /v1/account/orders/{client_id}`. در پاسخ نام شناسه `clientOrderId` است. پاسخ نامعلوم به ثبت سفارش نباید با ارسال مجدد کورکورانه دنبال شود؛ ابتدا باید سفارش قبلی تطبیق داده شود.
- [بازارها](https://developers.wallex.ir/docs/basic-services-markets): `GET /hector/web/v1/markets`؛ نوع بازار و دقت قیمت/مقدار را از متادیتا بخوانید.
- [کندل تاریخی](https://developers.wallex.ir/docs/basic-services-candles): `GET /v1/udf/history` با `symbol`، `resolution`، `from` و `to`. timestampهای این API بر حسب ثانیه‌اند. رزولوشن‌های REST با نام بازه‌های کانال کندل WS یکی نیستند.
- [کارمزد حساب](https://developers.wallex.ir/docs/basic-services-account-fee): `GET /v1/account/fee`؛ نرخ واقعی maker/taker باید از حساب و بازار گرفته شود. کارمزد صفر فرض نمی‌کنیم.
- [جزئیات طرح](https://developers.wallex.ir/docs/trade-credit-package-details): `GET /v1/prop/packages/{id}` شامل `unavailableMarkets` است. باید با فهرست چالش تقاطع گرفته شود؛ جای فهرست رسمی برگزارکننده را نمی‌گیرد.
- [کیف پول اعتباری](https://developers.wallex.ir/docs/trade-credit-wallet) و [جزئیات موجودی](https://developers.wallex.ir/docs/generated/sub-account-balances-details): حساب اصلی با حساب اعتباری متفاوت است. مستند تولیدشده مسیر `GET /v1/account/balances-detail` را معرفی می‌کند. دامنهٔ حساب و روش احراز هویت این مسیر باید هنگام ساخت کلاینت با کلید اختصاصی تأیید شود؛ به توضیح «بدون هدر سفارشی» صفحهٔ تولیدشده به‌عنوان مجوز دسترسی ناشناس به موجودی اتکا نمی‌کنیم.

## وب‌سوکت جدید

[مقدمه](https://developers.wallex.ir/docs/socket-intro)، [اتصال با SDK](https://developers.wallex.ir/docs/socket-connection)، [پروتکل خام](https://developers.wallex.ir/docs/socket-raw-protocol)، [توکن خصوصی](https://developers.wallex.ir/docs/socket-token).

- آدرس V2: `wss://api.wallex.ir/connection/websocket`، بدون اسلش انتهایی. نسخهٔ `/ws` منسوخ شده؛ قالب Socket.IO یا subscribe آرایه‌ای آن نباید با V2 ترکیب شود.
- کانال عمومی بدون توکن است؛ نمونه‌ها: `public:BTCTMN@trade`، `orderbook:BTCTMN@buyDepth` و `orderbook:BTCTMN@sellDepth`.
- هر اتصال V2 حداکثر ۶۴ کانال دارد. SDK مدیریت reconnect و ping/pong پروتکل را انجام می‌دهد. در پیاده‌سازی خام، قرارداد پیام خالی `{}` باید رعایت شود؛ زمان‌بندی ثابت ساختگی برای heartbeat تعریف نکرده‌ایم.
- عمق بازار و معاملات در قطع اتصال قابل بازیابی خودکار نیستند و subscribe اسنپ‌شات اولیه ندارد؛ پس همگام‌سازی REST پس از reconnect لازم است. فقط کندل‌ها تاریخچهٔ کوتاه دارند.
- توکن خصوصی V2 از `POST /v3/auth/token/refresh` با **کوکی احراز هویت کاربر** گرفته می‌شود؛ API key جای آن نیست. `ws_access_token` کوتاه‌عمر را نباید ثابت در `.env` گذاشت. در اسکلت فعلی از کوکی شخصی یا توکن خصوصی استفاده نمی‌کنیم؛ برنامهٔ اولیهٔ تطبیق سفارش، REST است.

## MCP

MCP برای اتصال مستقیم REST ضروری نیست. نشانی و قرارداد احراز هویت MCP را باید برگزارکننده بدهد؛ مقدار فرضی نساخته‌ایم. متغیرهای آن رزرو شده و غیرفعال‌اند؛ پشتیبانی transport/auth هنوز پیاده نشده است.

## محدودیت‌های این مرحله

تمام سقف‌ها و بودجه‌های API/LLM صرفاً تنظیمات آینده‌اند. پرکردن فایل، معامله یا تماس با مدل را آغاز نمی‌کند؛ محاسبهٔ کارمزد، تطبیق حساب، بررسی موجودی، precision/minimum order، محدودیت نرخ و کنترل ریسک باید در مرحلهٔ موتور پیاده‌سازی و آزمون شوند. برای قیمت و مقدار سفارش باید از decimal دقیق/رشته استفاده شود، نه محاسبات پولی با floating point معمولی JavaScript.
